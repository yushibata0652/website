1. The 30-second pitch
AeroLedger is a demo “mission control” app that audits aerospace invoices against historical launch-cost data.
An AI-style agent (built with LangGraph) checks each invoice. If the price looks normal, it auto-approves and writes it to a ledger. If the price looks suspicious (more than 25% over the historical baseline), it pauses and asks a human CFO for a decision. That decision is saved in memory so similar invoices can be auto-approved next time.

9:04 PMdata scraper5. The agent — explained like a flowchart
The agent is not a free-form chatbot. It’s a directed graph of steps with shared state (InvoiceState: id, vendor, part, amount, baseline, status, reason, anomaly flag).


Step A — check_memory
Ask Chroma: “Have we already learned a CFO rule for this vendor + part?”

If yes → mark APPROVED_BY_MEMORY and skip hard thinking later.
If no → continue empty-handed.

Step B — audit_pricing
Look up baseline cost in DuckDB from space_ledger_seed.csv.

Amount ≤ baseline × 1.25 → APPROVED
Amount > baseline × 1.25 → FLAGGED + anomaly_detected = true
No history found → also treat as anomaly (don’t auto-approve unknowns)

Step C — human_review (only if anomaly)
Uses LangGraph’s interrupt(...). That pauses the run mid-graph and waits for a resume command from the API. This is the human-in-the-loop moment.

Step D — commit_ledger
Insert the final decision into DuckDB’s reconciled_ledger table (audit trail).
Interview gold: “We used a state machine, not a single LLM prompt, so every branch is explicit, testable, and resumable.”
9:04 PMdata scraper6. Data layer (beginner-friendly)
DuckDB = “a database file, not a separate server”
On startup, db.setup():

Loads data/space_ledger_seed.csv into historical_space_procurement
Ensures reconciled_ledger exists for final outcomes

The seed CSV is real public data (Our World in Data LEO launch cost per kg): vehicle name, year, $/kg, vehicle class. In the demo UI, vendor ≈ launch vehicle, part ≈ class (Medium/Heavy/Small).

ChromaDB = “memory that matches by meaning, not exact string”
When the CFO writes a rule, we store:

embedding key: "vendor part"
metadata: the actual rule text

Later lookups query by similarity (cosine distance). If close enough (distance < 0.3), reuse the rule. That’s why similar invoices can skip human review.

LangGraph checkpointer (MemorySaver)
Lets a paused invoice keep its place. Resume uses the same thread_id (= invoice_id). Reset clears these so demos can replay.

11. Likely interview questions (and short answers)
Why LangGraph instead of one big prompt?
Explicit control flow, pauses, and auditable states beat opaque “just ask the model.”
Why interrupt instead of returning an error?
Errors end the job. Interrupt preserves progress and resumes with human input.
Why Chroma and DuckDB?
DuckDB = structured historical numbers. Chroma = fuzzy recall of past human decisions. Different jobs.
What breaks in production?
In-memory sessions, ephemeral disk, free-tier cold starts, and the simplified vendor/part mapping.
What’s the threshold logic?
amount > baseline * 1.25 → anomaly. Tunable business rule, not ML magic.

9:08 PMdata scraperPart 1 — The real-world story (why anyone would build this)
Imagine a procurement office for a space company. Invoices arrive constantly:

Vendor: who you’re paying (in the demo: often a launch vehicle name like Atlas V)
Part / line item: what you’re buying (in the demo: often a vehicle class like Medium)
Amount: how much they want

Some invoices are fine. Some are way over historical norms. Some are for things you’ve never seen.
Bad options:

Approve everything → waste money / fraud risk
Review everything manually → slow and expensive
Pure ML black box → hard to audit, hard to trust in regulated industries

AeroLedger’s pattern (what interviewers love):

Encode business policy as an explicit workflow (not vibes)
Automate confident cases
Escalate ambiguous / anomalous cases to a human
Persist the human decision so the system improves
Keep an audit trail of final outcomes

This is the same shape as fraud review, medical prior-auth, KYC escalation, content moderation queues, etc. Aerospace is the theme; the architecture is transferable.

9:08 PMdata scraperPart 6 — The agent in extreme detail (backend/agent.py)
6.1 Shared state
Every node reads/writes pieces of InvoiceState:

invoice_id, vendor_id, part_name, amount,
baseline_cost, status, reason, anomaly_detected
LangGraph merges each node’s returned dict into that state.

6.2 Graph topology
Nodes:

check_memory
audit_pricing
human_review
commit_ledger

Edges:

START → check_memory → audit_pricing
From audit_pricing, conditional:
if anomaly_detected → human_review
else → commit_ledger

human_review → commit_ledger → END

Compiled with MemorySaver() checkpointer so paused runs can resume.

6.3 Node: check_memory
Calls lookup_override(vendor_id, part_name).

Hit → set status APPROVED_BY_MEMORY, reason = stored rule, anomaly_detected=False
Miss → return {} (no change)

Important nuance: even after memory approval, the graph still flows into audit_pricing, but audit short-circuits if status is already APPROVED_BY_MEMORY.

6.4 Node: audit_pricing
Business rule engine:

If already approved by memory → do nothing
Else ask DuckDB for baseline
If no baseline → anomaly (baseline_cost=0, reason explains missing history)
If amount > baseline * 1.25 → FLAGGED, anomaly true, reason includes both numbers
Else → APPROVED, anomaly false

ANOMALY_THRESHOLD = 1.25 means 25% over baseline triggers human review.
Interview phrasing: “The threshold is a tunable policy constant, deliberately simple and auditable.”

6.5 Node: human_review + interrupts
decision = interrupt("CFO override required")
What interrupt means in plain English:

Stop the graph here
Persist progress via checkpointer (keyed by thread_id)
Return control to the API caller with an interrupt payload
Later, resume with Command(resume=...) carrying the human’s input

After resume, node maps the decision into:

APPROVED_BY_CFO or REJECTED
plus a reason string

6.6 Node: commit_ledger
Inserts one row into reconciled_ledger with timestamp. This is your audit log of what the system finally decided.

6.7 Why not “just call GPT”?
You can say:

Deterministic policy steps are cheap, testable, explainable
Human pause points need a real workflow runtime
LLMs can still help write override text or classify edge cases later — but the skeleton should be a graph

AeroLedger currently uses rules + vector memory, not an LLM call in the hot path. That’s a feature for demos: fewer moving parts, no API key required.
9:08 PMdata scraperPart 7 — Memory system deep dive (backend/memory.py)
What is stored?
Collection: cfo_override_rules
On save (save_override):

id: "{vendor}::{part}"
document (embedded text): "{vendor} {part}" only
metadata: { vendor_id, part_name, rule } where rule is the CFO’s natural-language decision
Why embed only vendor+part, not the rule text?
Comment in code says it clearly: if you embed the long rule, similarity gets diluted by wording length. Embedding the lookup key makes distance measure “is this the same kind of line item?”

Lookup algorithm
Embed query "vendor part"
Ask Chroma for nearest neighbor (n_results=1)
If distance ≥ 0.3 → treat as no match
Else return metadata rule

Distance space: cosine (hnsw:space: cosine).

What “learning” means here
Not model training. It’s case-based memory:

Human decides once
System stores the association
Similar future invoices can short-circuit to auto-approve with APPROVED_BY_MEMORY

Reset
clear_overrides() deletes all IDs in the collection. Used by /reset-demo.

Production caveats (say these unprompted)
Free Render disk can be wiped on redeploy → memory not durable
Similarity threshold 0.3 is heuristic
Exact vendor string mismatches still matter a lot
No user/tenant isolation in the collection
9:08 PMdata scraperPart 8 — Database deep dive (backend/db.py)
Two tables, two jobs
1) historical_space_procurement

Built from CSV every setup
Read-only reference data for baselines

2) reconciled_ledger

Append-only style outcomes of processed invoices
Columns: invoice_id, vendor_id, part_name, amount, status, timestamp

Baseline lookup strategy (get_baseline_cost)
Prefer exact match: Entity = vendor_id AND Launch vehicle class = part_name, latest Year
Fallback: treat vendor or part alone as Entity, latest year
If still nothing → raise ValueError (agent turns this into an anomaly)

This layered lookup makes the demo more forgiving when the UI’s naming isn’t perfect — and is a good talking point about graceful degradation.

Why DuckDB?
Local file, zero ops
Excellent CSV → table ergonomics (read_csv_auto)
Fine for demo analytics / lookups
Not a claim that you’d use DuckDB as your sole prod OLTP store forever (Postgres/etc. would be normal later)

9:09 PMdata scraperPart 10 — Frontend deep dive (frontend/app/page.tsx)
It’s one big client component
"use client" at top — browser React, not server-rendered business logic. Makes sense because almost everything is interactive session/batch state.

Session handling
Uses sessionStorage + useSyncExternalStore:

Server snapshot always “signed out” (avoids hydration mismatches)
Client reads token from storage
Sign-out also best-effort calls /logout

Batch runner design (important engineering detail)
runBatch(startIndex) loops invoices sequentially.
Why sequential?

A halt must stop the world for CFO input
Parallel approvals would race interrupts and confuse UX

Uses rowsRef so invoices added mid-run can still be seen by the loop (avoids stale closure).
Phases per row:

queued → waiting
running → API call in flight
cleared → finished (approved/rejected/etc.)
halted → needs CFO
error → network/API failure

When requires_human:

mark row halted
set interrupt panel state
return (stop batch)
after CFO submit, resume loop at interrupt.index + 1

Shows invoice id, vendor, part, invoiced amount, baseline, and variance multiplier. Operator types free-text rule and submits to /resolve-interrupt.

9:09 PMdata scraperPart 14 — Extended interview Q&A
Q: Is this an AI agent?
A: It’s an agentic workflow: stateful multi-step decisioning with tools/memory and human escalation. It does not currently call an LLM in the critical path; memory is vector similarity over past CFO rules.
Q: Why LangGraph?
A: Durable branching, interrupts, checkpointed threads, and clear node boundaries. Better than a pile of if-statements once human resume exists.
Q: How do you prevent double-spend / replaying invoices?
A: Thread id = invoice id + checkpoint memory. Reset clears threads for demos. Production would add idempotency keys and durable store constraints.
Q: What happens if two CFOs act at once?
A: Current demo is single-operator, in-memory sessions. Production needs authZ, locking around a paused thread, and audit of who approved.
Q: How would you add an LLM?
A: Optional node that drafts an override recommendation or explains variance in plain English — still keep thresholding + interrupt as source of truth.
Q: How do you test this?
A: Unit-test threshold routing; integration-test invoke→interrupt→resume; UI test batch halt/resume; golden tests with fixed CSV fixtures.
Q: Biggest technical risk in the current deploy?
A: Free-tier cold start + ephemeral disk + demo auth. Architecture is sound; durability/security need hardening.
Q: Why Chroma distance 0.3?
A: Tunable precision/recall knob. Too low → rarely reuse memory; too high → wrong rule applied. Would calibrate with labeled pairs.
Q: What’s the data model smell?
A: Using launch-vehicle $/kg as “invoice baseline” is metaphorical. Next step: real vendor/part master data and historical PO lines.
